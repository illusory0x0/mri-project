# Frontend tooling: stay minimal (vanilla + esbuild)

Status: accepted
Date: 2026-09-13

**Context.** The only frontend artifact is the static `eval/report.html`
generated by `eval/report.ts`; its client JS was an inline `CLIENT` string.
An interactive projectional-editor UI may come later.

**Decision.** The client now lives in `eval/report.client.ts` and is bundled by
esbuild into `dist/eval/report.client.js`, which `eval/report.ts` inlines into
the HTML. A separate `eval/tsconfig.client.json` type-checks it with the `DOM`
lib, so the Node tsconfig stays DOM-free. Introduce no framework. If an
interactive editor UI is built, use Vite + TypeScript + Preact or Solid.

**Considered options, and why not.**

- **Next.js / Nuxt / Remix** — built for SSR, routing, SEO, and full-stack
  apps; this is a local, single-purpose tool UI, so the framework costs far
  more than it returns.
- **React plus its ecosystem** (Redux/Zustand, styled-components, MUI/AntD) —
  runtime and dependency weight dwarf the actual UI, and component libraries
  lock in visual choices and upgrade cadence. Preact/Solid offer a similar API
  at a fraction of the size.
- **Tailwind** — pays off across many pages and components; for one small tool,
  hand-written CSS variables are lighter and easier to control.
- **Vite for the static report** — a generate-and-open HTML file needs no dev
  server, and esbuild already bundles it.
- **JSDOM / Playwright and other UI test harnesses** — the only GUI is a
  read-only report; add these when there is real interaction to test.
- **State-management, form, and i18n libraries** — no real need yet; the editor
  is stateless and the UI state is tiny.

**Revisit when.** An interactive editor UI starts being built (adopt Vite +
Preact/Solid), or the report grows interactive logic that needs tests.
